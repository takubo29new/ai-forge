# テスト仕様書

| 項目 | 内容 |
| --- | --- |
| 文書名 | ai-forge テスト仕様書 |
| 対象システム | ai-forge(統合AI開発支援プラットフォーム) |
| 版数 | 1.0.0 |
| 対応バージョン | v1.1.0 |
| 作成日 | 2026-08-27 |

本書は、ai-forgeに実装済みの自動テスト(Vitest)を正式なテスト仕様の形式でカタログ化したものである。新規にテストケースを設計するのではなく、既存の`it`/`test`ブロックをテストケースとして採録し、テスト種別・テスト観点を付与して整理する。要件は[要件定義書](./requirements-definition.md)、機能の詳細な処理フローは[基本設計書](./basic-design.md)を参照。したがって、テストケースの粒度・網羅範囲は実装済みの自動テストに対応しており、本書に無い観点は現時点で自動テストの対象外であることを意味する(5節参照)。

---

## 1. テスト種別

| 区分 | 実行コマンド | 設定ファイル | 対象・特徴 |
| --- | --- | --- | --- |
| 単体テスト | `npm test`(`vitest run`) | `vitest.config.mts` | `src/**/*.test.ts`。DBアクセスを行わず、純粋な関数・スキーマ検証・フォーマットロジックを対象にする。外部APIクライアントは基本的に呼び出されない(モデルの型検証や文字列処理が中心) |
| 結合テスト | `npm run test:integration`(`vitest run --config vitest.integration.config.mts`) | `vitest.integration.config.mts` | `src/**/*.integration.test.ts`。実際のPostgres(`DATABASE_URL`)にPrisma経由で接続し、API RouteのHandler関数(`GET`/`POST`/`PATCH`/`DELETE`)を直接呼び出して検証する。GitHub・Anthropic・Voyage AIの各外部APIクライアントは`vi.mock`でモックし、実際のネットワーク呼び出しは行わない |

いずれもCI(`.github/workflows/ci.yml`)で`push`・`PR`のたびに実行され、結合テストの実行時はPostgresのサービスコンテナに対して`prisma migrate deploy`を適用してから`test:integration`を実行する。テスト用のユーザー・プロンプト・リポジトリの作成や後始末は`src/test/db-helpers.ts`(`createTestUser`・`createTestPrompt`・`createTestRepository`・`cleanupTestUser`)に共通化されている。

## 2. テスト観点

実装済みのテストから抽出した観点は以下のとおりである(架空の観点は挙げていない)。

| 観点 | 内容 | 主な対象 |
| --- | --- | --- |
| 正常系 | 想定どおりの入力に対し、期待どおりの出力・DB状態になること | 単体・結合の両方 |
| 認証(401) | セッションが無い場合に401を返すこと | 全結合テストファイルでほぼ共通 |
| 認可・所有者チェック(404) | 他ユーザーが所有するリソースへのアクセス・操作には、存在の有無を推測させないよう404を返すこと | プロンプト・カテゴリ・リポジトリ・レビュー・評価・通知・ドキュメント系 |
| 入力バリデーション(400) | 必須項目の欠落・空文字・不正な値・対応していない形式・サイズ上限超過を拒否すること | カテゴリ/プロンプト/評価/チャットのPOST系 |
| 一意制約・重複(409/DB制約) | 同名リソースの重複作成の拒否、DBの部分ユニークインデックスによる重複防止 | カテゴリ名、ドキュメントの`sourcePath`重複 |
| レート制限(429) | ユーザー×用途単位の呼び出し回数上限に達した場合に429を返すこと | 実行・改善提案・評価のPOST系 |
| 外部API異常系 | AI呼び出し(Anthropic)・埋め込み生成(Voyage AI)の失敗時の挙動(FAILED記録、502、ベストエフォート継続) | 実行・レビュー・評価・ドキュメント登録/同期系 |
| ベストエフォート処理の継続性 | 埋め込み生成など副次処理が失敗しても、主目的の処理(保存・実行結果)自体は成功として扱われること | プロンプト更新・プロンプト実行・レビュー実行 |
| バックグラウンド処理 | 重い処理は`PENDING`を即座に返し、非同期に完了させること | AI評価作成 |
| 冪等性 | 同じ操作を繰り返しても結果が安定していること(共有トークンの再発行、埋め込みの二重生成防止) | 共有リンク発行、埋め込みバックフィル |
| データ整合性(カスケード/SetNull) | 親レコード削除時の子レコードの扱いが設計どおりであること | カテゴリ削除→SetNull、プロンプト/ドキュメント削除→カスケード削除 |
| セキュリティ(暗号化) | 機微情報がDBに平文で残らないこと | AI評価結果(`summary`・`EvaluationFinding.body`) |
| スコープ絞り込み | リポジトリ単位・ユーザー単位でデータが正しく絞り込まれること | チャットの`repositoryId`絞り込み、横断検索 |
| 境界値 | ちょうど上限に達した場合の挙動 | 画像/PDFサイズ上限、レート制限の上限件数 |

## 5. カバレッジ状況・既知の対象外事項

自動テストの範囲は上記のとおりだが、以下は自動テストの対象外であり、手動確認・実機検証で担保している。

- **UI/ブラウザ操作**: 画面遷移・フォーム入力・トースト表示・確認ダイアログ等のフロントエンド動作は自動テストの対象外で、各機能の実装セッションごとにユーザーがブラウザで実機確認している(WORKLOG.mdに記録)。
- **本番環境固有の問題**: Vercel Functionの実行時間・リージョン・環境変数の扱い等、本番デプロイ特有の問題は結合テストでは再現されない([quality-improvements.md](./quality-improvements.md)に個別の対応記録がある)。
- **Voyage AI・GitHub・Anthropicの実際のレート制限/仕様変更**: 結合テストではこれら外部APIを`vi.mock`でモックしており、実際のAPI側の制限値・レスポンス形式の変更は検知できない。
- **GitHub Appユーザートークンの実際の失効・自動更新**: `refresh_token`によるトークン自動更新ロジック(`src/lib/github.ts`)自体の単体テストは無く、本番での実際の失効・更新は運用中に確認されている。
- **並行リクエストによるレート制限のレース条件**: `RateLimitBucket`のアトミックな`upsert`方式は導入時に手動での並行リクエスト検証で確認されており(WORKLOG.md 2026-08-23分)、自動テストとしては再現していない。
