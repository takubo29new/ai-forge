## 1. はじめに

### 1.1 目的

本書は、ai-forgeの開発にあたり実現すべき機能・非機能の要件を定義するものである。実装の詳細(画面・DB・API)は[基本設計書](./basic-design.md)に、各Phaseの設計判断の経緯は`docs/phaseN-design.md`各書に記載する。

### 1.2 背景

AIに投げるプロンプト、AIによるコードレビュー、社内ドキュメント検索チャットボットは、いずれも「Claude(Anthropic API)にプロンプトを投げて構造化された結果を得る」という共通の仕組みの上に成り立つ。これらを個別のツールとして作るのではなく、1つのプラットフォームとして統合し、プロンプト資産・レビュー履歴・ドキュメントを相互に活用できるシステムとして構築する。

### 1.3 想定読者

本書は開発担当者・レビュー担当者を主な読者として想定する。

---

## 2. システム概要

### 2.1 システムの位置づけ

ai-forgeは、以下3つの機能を段階的に統合した単一のWebアプリケーションである。

1. **プロンプト管理ツール**(Phase 1) — AIに投げるプロンプトをコードのように管理・改善する
2. **AIコードレビュー/リファクタリング提案ツール**(Phase 2) — GitHubリポジトリのコードをAIが解析・指摘する
3. **RAG構成のドキュメント検索チャットボット**(Phase 3) — 設計書やレビュー履歴をベクトル検索し、自然文で質問応答する

上記3機能をデータレベルで統合する**Phase 4(統合基盤の強化)**、コードレビューの仕組みを画像・テキスト・PDFなど汎用の入力形式に拡張する**Phase 5(汎用AI評価ツール)**を経て、現行のv1.1.0に至る。

### 2.2 利用者

単一ユーザーが自身のGitHubアカウントでログインし、自分のプロンプト・接続リポジトリ・ドキュメント・評価結果を管理する、シングルテナント型の利用形態を前提とする(マルチユーザーでの共同編集は対象外)。

### 2.3 用語定義

| 用語 | 定義 |
| --- | --- |
| プロンプト(Prompt) | Claudeに投げる指示文のテンプレート。バージョン管理される |
| 実行(Execution) | プロンプト・AIレビュー・AI評価いずれかによるClaude API呼び出しの記録単位 |
| レビュー(Review) | GitHub PRの差分に対するAIコードレビューの実行単位 |
| 評価(Evaluation) | 画像・テキスト・PDFいずれかの入力に対する汎用AI評価の実行単位 |
| ドキュメント(Document) | RAG検索チャットの検索対象として取り込んだ設計書・メモ等 |
| 埋め込み(Embedding) | ベクトル検索のためにテキストを数値ベクトル化したもの(Voyage AI `voyage-3`を使用) |
| 通知(Notification) | バックグラウンド処理の完了等をユーザーに知らせる記録 |

## 3. システム化の狙い

| 狙い | 内容 |
| --- | --- |
| AI呼び出しの一元化 | Phase 1で構築する「プロンプト→Execution→結果」の仕組みを、Phase 2(レビュー)・Phase 5(評価)でも一貫して再利用し、実装・運用コストを抑える |
| 実務文脈に沿ったRAG | 汎用チャットボットとの差別化として、自社(自分)で蓄積したレビュー履歴・設計書・プロンプト資産を検索対象にする |
| コードに限らない汎用評価 | Phase 2で確立した「プロンプトを選んでClaudeに評価させる」パターンを、画像・テキスト・PDFなど他の入力形式にも拡張し、レビュー・評価という行為そのものを汎用化する |
| 個人情報保護への配慮 | 評価対象が履歴書・契約書・人物写真など個人情報を含みうる入力に広がったことを踏まえ、保存方針(永続化しない・暗号化する)を明確にする |

## 4. 機能要件

### 4.1 機能一覧(Phase別)

#### Phase 1: プロンプト管理ツール

| No. | 機能名 | 概要 |
| --- | --- | --- |
| 1-1 | GitHub OAuthログイン | GitHubアカウントでのサインイン・サインアウト |
| 1-2 | カテゴリ管理 | プロンプトの分類ラベルの作成・編集・削除 |
| 1-3 | プロンプトCRUD | プロンプトの登録・編集・削除、カテゴリ紐付け |
| 1-4 | バージョン履歴 | プロンプト編集のたびに新バージョンとして保存し、履歴を保持する |
| 1-5 | プロンプト実行 | 選択したバージョン・モデルでClaudeを呼び出し、結果を表示する |
| 1-6 | 変数展開 | 本文中の`{{変数名}}`を検出し、実行時に入力フォームを生成して値を埋め込む |
| 1-7 | 実行履歴 | 過去の実行結果・使用モデル・トークン数・実行時間を一覧表示する |

#### Phase 2: AIコードレビューツール

| No. | 機能名 | 概要 |
| --- | --- | --- |
| 2-1 | GitHubリポジトリ連携 | GitHubリポジトリの接続・解除、オープンなPR一覧の取得 |
| 2-2 | AIレビュー実行 | 選択したPRの差分とプロンプトからClaudeにレビューさせ、指摘事項を構造化して取得する |
| 2-3 | レビュー結果表示 | 指摘事項をファイルパス・行・重要度(CRITICAL/WARNING/INFO)別に一覧表示する |
| 2-4 | レビュー結果の蓄積・可視化 | リポジトリ単位で累計指摘件数・直近レビューの推移・指摘の多いファイルを表示する |
| 2-5 | レビュー結果の共有リンク | 成功したレビューを、ログイン不要の読み取り専用URLで公開する |

#### Phase 3: RAG検索チャットボット

| No. | 機能名 | 概要 |
| --- | --- | --- |
| 3-1 | ドキュメント登録 | タイトル・本文の手動貼り付けによるドキュメント登録、見出し単位でのチャンク分割・埋め込み生成 |
| 3-2 | 設計書の自動同期 | ai-forge自身のリポジトリ・接続済みGitHubリポジトリのdocs配下/READMEを取り込む |
| 3-3 | 既存データの埋め込みバックフィル | 埋め込み未生成のレビュー指摘・プロンプトバージョン・実行結果を一括処理する |
| 3-4 | RAG検索チャット | 自然文の質問をベクトル検索し、関連するドキュメント・レビュー指摘等を根拠にClaudeが出典付きで回答する |
| 3-5 | 統合ダッシュボード | プロンプト数・接続リポジトリ数・累計指摘件数・登録ドキュメント数を横断表示する |

#### Phase 4: 統合基盤の強化

| No. | 機能名 | 概要 |
| --- | --- | --- |
| 4-1 | RAG検索対象の拡張 | プロンプトバージョン本文・プロンプト実行結果もRAG検索チャットの対象に加える |
| 4-2 | プロジェクト単位のドキュメント管理 | 接続済みGitHubリポジトリごとにdocs配下を同期し、チャットの検索対象をリポジトリ単位で絞り込めるようにする |
| 4-3 | プロンプト改善提案 | 過去のレビュー指摘の傾向をClaudeに分析させ、プロンプト本文の改善案を生成する |
| 4-4 | チャットからの直接アクション実行 | チャットの自然文発話からAIレビュー実行の意図を検出し、確認のうえ実行する |

#### Phase 5: 汎用AI評価ツール

| No. | 機能名 | 概要 |
| --- | --- | --- |
| 5-1 | 画像評価 | 料理写真・イラスト等の画像とプロンプトから、Claude Visionで観点別コメント・総評を取得する |
| 5-2 | テキスト評価 | 歌詞・文章等のテキストとプロンプトから、同様に評価結果を取得する |
| 5-3 | PDF評価 | 履歴書・契約書・論文等のPDFとプロンプトから、同様に評価結果を取得する |
| 5-4 | バックグラウンド実行 | 評価実行はレスポンスをすぐ返し、実際のAI呼び出しは非同期で継続する |
| 5-5 | 通知センター | バックグラウンド処理の完了をヘッダーの通知アイコン(未読バッジ)で知らせる |
| 5-6 | 評価結果の共有リンク | 成功した評価を、ログイン不要の読み取り専用URLで公開する |
| 5-7 | プロンプトテンプレート集 | 評価用途別の叩き台プロンプトを新規作成画面から選択できる |
| 5-8 | 評価結果の暗号化保存 | 評価結果のテキストをアプリケーション層で暗号化してDBに保存する |

## 5. 非機能要件

### 5.1 性能要件

| 項目 | 要件 |
| --- | --- |
| AI呼び出しの応答性 | レイテンシの大きい処理(画像・PDF評価等)は同期応答とせず、`PENDING`状態を即座に返してバックグラウンドで継続する |
| 一覧取得の上限 | 無制限取得によるDB負荷を避けるため、一覧系クエリに上限件数(`LIST_LIMIT`)を設ける |
| 主要外部キーへのインデックス | 頻繁に検索条件となる外部キー列にインデックスを付与する |

### 5.2 可用性要件

| 項目 | 要件 |
| --- | --- |
| デプロイ先 | Vercel(本番)。DBと同一リージョン(東京)でFunctionを実行し、リージョン間往復によるレイテンシを避ける |
| エラー時の継続性 | AI呼び出しや埋め込み生成など副次的な処理の失敗が、主目的の処理(レビュー結果の保存等)を巻き込んで失敗しないようベストエフォート方針を徹底する |

### 5.3 セキュリティ要件

| 項目 | 要件 |
| --- | --- |
| 認証 | GitHub OAuthによるログインを必須とする(NextAuth.js) |
| 認可 | 全リソース(プロンプト・リポジトリ・レビュー・評価等)は所有者(`userId`)単位でスコープし、他ユーザーのリソースへはアクセスできないようにする |
| GitHubアクセストークンの保護 | DBに保存するGitHubアクセストークン・リフレッシュトークンはAES-256-GCMで暗号化する |
| AI評価結果の保護 | 評価対象が個人情報(履歴書・契約書・人物写真等)を含みうるため、評価結果のテキストはAES-256-GCMで暗号化して保存する |
| 画像・PDFの非永続化 | アップロードされた画像・PDFそのものはDB/ストレージに保存せず、リクエスト内でClaudeに渡すのみとする |
| 共有リンクの取り扱い | 読み取り専用の公開URLを発行する機能では、作成前に非公開情報が含まれていないかの確認を必須とする |
| レート制限 | AI呼び出し系API・クライアントエラー報告APIに、ユーザー×用途単位の呼び出し回数上限を設ける |
| 個人情報アラートの扱い | 共有リンク作成時にAIによる自動的な個人情報検出・警告は行わない(誤検知・見逃しのリスクを理由に不採用と判断) |

### 5.4 運用・保守性要件

| 項目 | 要件 |
| --- | --- |
| エラーの追跡可能性 | 想定外エラーをサーバー・クライアント双方で収集し、再現なしに原因調査できるようにする |
| ドキュメントの一元的な整合性 | README・要件定義書・基本設計書・各Phase設計書・DB設計書間で機能の実装状況の記述に矛盾が生じないよう保守する |
| バージョン管理 | 節目ごとにセマンティックバージョニング(`vX.Y.Z`)でタグ付けし、リリース内容を記録する |
| 自動テスト | 単体テスト・結合テストにより、認可・バリデーション・主要な成否分岐を継続的に検証する(詳細は[テスト仕様書](./test-specification.md)) |

### 5.5 費用・コスト要件

| 項目 | 要件 |
| --- | --- |
| コストの可視化 | Claude・Voyage AIの利用量(トークン数・埋め込み件数)を可視化する |
| 金額換算の扱い | Anthropic公式の現行料金表(`src/lib/model-pricing.ts`)から概算コスト($)を算出して表示する(Issue #109)。プロンプトキャッシュ・バッチAPI等の割引は考慮しないため実際の請求額とは一致しない旨をUI上に明記する |

## 6. 制約事項・前提条件

| No. | 内容 |
| --- | --- |
| C-1 | 音声入力への対応は行わない(Claude APIが音声そのものを解析できないため) |
| C-2 | アップロードした画像は結果画面での再表示用に永続化しない(個人情報保護の観点、詳細は`docs/phases/phase5-design.md`「見送った拡張候補」を参照) |
| C-3 | マルチユーザーでの共同編集・ロール管理は対象外とする |
| C-4 | GitHub連携はGitHub Appのユーザートークン(約8時間で失効)を前提とし、`refresh_token`による自動更新を行う |
| C-5 | 対応ブラウザはモダンブラウザ(最新のChromium系・Safari・Firefox)を前提とする |
